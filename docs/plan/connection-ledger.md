# 연결 장부 — EDIM 전체가 유기적으로 도는가

> 회장님 지시(2026-09-19): "마지막으로 다 연결하고 EDIM 전체가 유기적으로 돌아가야 하는 것도 잊어선 안 돼."
> 구역을 하나씩 채우는 것과 **구역 사이가 이어지는 것**은 다른 일이다. 이 장부는 '이어짐'만 본다. Phase가 끝날 때마다 갱신하고, 마지막에 **P6 통합**으로 닫는다.

## 승인된 순서 (2026-09-19)
P3-a 플랫폼 관리자 계층 + DB①/② 분리·역류 차단(구조만) → P4 치수 전파 도면·견적·구매 → P3-b 학습 1수준 + 프로젝션(회장님 DXF 연구 결과 후) → P3-c Special 슬롯(사장님 D1 후) → **P6 통합(유기 연결)** → P5 발표.

## 판정 기준
- **이어짐** = 앞 구역의 산출이 **저장된 데이터로** 다음 구역의 입력이 된다(사람이 다시 입력하지 않는다, 화면 상태에만 의존하지 않는다).
- **약함** = 이어지긴 하나 화면(브라우저) 상태를 거치거나, 매번 다시 계산하거나, 한 방향만.
- **없음** = 연결 0.

## P6 통합의 완료 기준 (제안)
1. **금실(golden thread) 1회 주행**: 한 제품 코드가 *등록 → 조립·Rev 저장 → Macro 승인·Run → BOM 스냅샷 → 도면·견적 → 구매 요청 → 승인 기록*까지, **중간에 사람이 값을 다시 넣지 않고** 저장된 데이터만으로 이어진다. e2e 한 시나리오로 고정.
2. **추적**: 최종 견적·구매 요청 한 줄에서 거꾸로 *어느 스냅샷 → 어느 Rev → 어느 카탈로그 지문 → 어느 승인 매크로 revision*인지 화면에서 따라갈 수 있다.
3. **변경 전파**: 표 한 칸 또는 치수 하나를 바꾸면 BOM·도면·원가·구매 수량이 함께 바뀌고, 이전 스냅샷은 그대로 남는다.
4. 위 표에 **'없음' 0 · '약함' 0**.

### 정정 — P4-a 의 "저장된 코드 Revision → BOM Run: 이어짐" 은 과장이었다
- **무엇이 틀렸나**: P4-a 는 스냅샷에 "그 노드의 **최신** 개정"을 무조건 박았다(`latestRevisionId`). 실측: `…630SS` 로 돌린 스냅샷 4건 전부에 Rev B(`…630AL`)가 찍혀 있었다. 고리는 이어져 있었지만 **틀린 곳으로** 이어져 있었다.
- **어떻게 발견했나**: P4-b 견적서 인쇄본을 눈으로 검증하다가 — 발치의 코드 개정 근거가 견적 코드와 맞지 않았다. 테스트는 "id 가 박히는가"만 봤지 "맞는 id 인가"를 보지 않았다.
- **어떻게 고쳤나**: `revisionIdForSlots` — **그 슬롯 조합으로 저장된** 개정만 근거로 삼고, 없으면 null(최신을 대신 박지 않는다). `drawing:test` 12 → 14 · e2e S22f(Rev A 슬롯으로 돌리면 Rev A 가, 저장한 적 없는 조합이면 빈 값이 견적서에 찍힌다).
- **남는 한계**: 비교는 슬롯 값의 완전 일치다. 개정은 A~E 만 저장하고 실행은 F 까지 보낼 수 있어, 같은 제품이라도 F 가 붙은 실행은 근거 개정이 비게 된다. 개정에 F 를 넣을지는 **회장님 결정**이 필요하다(RCCS 문법 사안).
