### 정정 — P4-a 의 "저장된 코드 Revision → BOM Run: 이어짐" 은 과장이었다

- **어떻게 발견했나**: P4-b 견적서 인쇄본을 눈으로 검증하다가 — 발치의 코드 개정 근거가 견적 코드와 맞지 않았다. 테스트는 "id 가 박히는가"만 봤지 "맞는 id 인가"를 보지 않았다.

- **남는 한계**: 비교는 슬롯 값의 완전 일치다. 개정은 A~E 만 저장하고 실행은 F 까지 보낼 수 있어, 같은 제품이라도 F 가 붙은 실행은 근거 개정이 비게 된다. 개정에 F 를 넣을지는 **회장님 결정**이 필요하다(RCCS 문법 사안).

#### 수리 (2026-09-21 · 위 추정은 절반만 맞았다)
- **hierarchy — 기대값이 낡음(제품 정상).** `eee26c1`(L3 프로젝트 엔진)이 시드 root 아래에 프로젝트 노드를 추가해 root 기준 자식이 1 → 2 가 됐는데 테스트가 `1` 을 못 박고 있었다. "만들고(+1) 옮기면(−1) root 는 처음 그대로이고 AHU-02 는 root 에 없다"는 **기준선 상대 단언**으로 바꿨다.
- **macro — 제품 결함(테스트가 옳았다).** `approve()` 가 "그 노드 모든 행의 최대 revision + 1" 을 매겼는데 초안의 열 기본값이 1 이라 **첫 승인이 r2** 로 나왔다. 테스트와 구현은 같은 커밋(`14e346d`, 7/6)에서 나왔고 그 테스트는 Postgres 가 없어 한 번도 돈 적이 없다. 개정 번호는 **승인된 적 있는 행(approved·superseded)만** 세도록 고쳤고, "반려된 초안은 번호를 소비하지 않는다(r1 → r2 → r3)" 단언을 더했다. 스키마 변경 없음. 화면에 보이던 `approved r3 / superseded r2` 는 이제 `r2 / r1` 이다(DEMO.md 장면 4 의 "r1 탑재 → 라이브 승인 시 r2" 서술이 비로소 사실이 됐다).

#### 변경 전파를 한 시나리오로 (2026-09-21 · e2e S30a~g · 99 → 106단계)

**단서 — 한 칸이 네 산출물 전부에 닿지는 않는다.** `filterQty` 는 BOM·원가·구매에, 치수 `W` 는 도면에만 닿는다. 그래서 "한 칸"이 아니라 "한 번의 저장(두 칸)"이다.

**이 시나리오가 잡은 것 두 가지**
1. **결함(가드로 막음 · 근본 해법은 승인 대기)** — 도면은 줄·코드를 스냅샷에서 읽지만 **치수는 현재 등록 표에서** 읽는다(`drawing-source.ts`). 그래서 BOM 이 승인된 뒤 치수 표를 고치면 **옛 승인으로 새 치수의 도면이 발행될 수 있었다**(P6 의 "승인 뒤 고치면 옛 승인으로 못 나간다"가 치수에 대해선 거짓이었다). 지금은 스냅샷의 카탈로그 지문이 현재와 다르면 도면 생성·등록을 **409 로 거절**한다(스키마 변경 없음 · S30f). 이미 등록된 도면은 내용이 저장돼 있어 무관. 부작용: 표의 *어느* 칸이든 바뀌면 옛 스냅샷으로는 도면을 새로 못 그린다(다시 BOM Run → 다시 승인). 근본 해법 = `bom_code_run` 에 치수를 함께 박는 열(마이그레이션 0011 · Tier B) — 그때 이 가드는 걷어낸다.
2. **설계 사안(미결 · 회장님 결정)** — 같은 단면 치수가 두 칸에 있다: 전 사이즈 12행에서 `cap.face`(BOM 사양 "2472×2472" 가 읽음) = `dim.W`(도면이 읽음). W 만 고치면 도면은 2600, BOM 사양은 2472 로 남는다 — "치수 하나를 바꾸면 관련 치수 전부에 전파"와 어긋난다. 권고: BOM 사양이 `dim.W/H` 를 읽게 참조만 옮기고 `cap.face` 열은 남긴다(열을 지우면 매크로의 열 글자 주소가 밀린다).
