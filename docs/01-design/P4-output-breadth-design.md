## 2. 설계의 축 하나

**모든 산출물은 BOM 스냅샷 하나(`runId`)에서 나온다.**

```
코드 Rev ──┐
           ├─→ [BOM Run: 서버가 매크로까지 실행] ─→ bom_code_run (스냅샷)
등록 표  ──┘                                            │
                                    ┌───────────────────┼───────────────────┐
                                  도면(DXF)          견적(PCR/Quotation)   구매 요청(PR)
```

- 지금: 도면·원가·EBOM이 **각자 슬롯에서 매번 다시 계산**한다. 그래서 같은 화면인데 근거가 셋이다.
- P4: 스냅샷 id를 입력으로 받는다. 스냅샷이 없으면 산출물을 못 만든다(422). 견적 합계는 "다시 계산한 값"이 아니라 **그 스냅샷에 저장된 cost**다 → 카드 값과 문서 값이 어긋날 수 없다.

이 한 줄이 P6 통합의 완료 기준 2번(추적)과 3번(변경 전파)을 미리 만족시킨다.

## 3. 범위를 둘로 나누자 (권고)

승인된 카드는 5항목이고 엘 추정 2~3세션이다. P3-a처럼 **한 번에 검증 가능한 단위**로 자른다.

### P4-a — 치수 전파 + 도면 (먼저)
1. **치수 표 등록**: 제품 코드의 등록 표에 `Dim` 종류 표를 하나 더 둔다. 모양은 p16·p51의 그 표 그대로 — `Item | A | B | C | D | E`, 행은 사이즈(560·630·710·800). **새 화면을 만들지 않는다**(회장님이 승인한 "표 모양 통일"의 연장).
2. **DXF가 등록 치수를 읽는다**: `buildDxf`가 상수 대신 스냅샷 + 치수 표에서 A~E를 가져온다. 표에 행이 없으면 **거부(422)**하고 사유를 말한다(추측 금지 — P1에서 세운 규칙).
3. **도면 2장**: 평면도(현행 개선) + **조립도**(p38·p40 — 외형 + Item 표 ①~⑤가 도면 안에 들어간다). 조립도의 Item 표는 BOM 스냅샷 줄에서 나온다.
4. **`drawing` 테이블**(p24 컬럼 그대로): 도면번호·유형·축척·크기·`current_rev`·`status`(작성중/검토/승인/발행)·`bom_run_id`. **발행 상태는 잠금** — 수정 시도는 서버가 409.
5. **약함 3건 해소**: ① BOM Run이 서버에서 승인 매크로를 직접 실행(클라이언트 `macroValue` 폐기) ② EBOM·Cost가 `runId`를 받는다 ③ 스냅샷에 `code_revision_id` 기록.

**DoD** — 치수 한 칸(710행의 B)을 바꾸고 도면을 다시 뽑으면, 전후 DXF를 파싱해 **해당 엔티티만** 달라진다. 발행된 도면은 수정이 거부된다. 연결 장부 약함 3 → 0.

### P4-b — 견적 · 구매 (그다음)
6. **Quotation / PCR**(p66): 스냅샷 cost를 그대로 쓰는 인쇄용 문서 1종. 합계가 Cost 카드와 **한 원도 다르지 않다**(같은 값을 읽으므로 구조적으로 보장).
7. **Tech Data 1종**(p15~16): 매크로 결과값 표 — 승인 매크로 revision과 입력을 함께 박는다.
8. **구매 요청**(p51~52): 스냅샷 줄 중 `kind='purchase'` 줄만 모아 `purchase_request`(PR 번호·상태·품목·수량·필요일) → 화면 목록 + Export.
9. 문서도 `status` 4단계와 발행 잠금을 공유한다.

**DoD** — 견적 합계 = Cost API 값 · PR 품목 수 = 스냅샷의 구매 품목 수 · 발행 문서 수정 차단.

## 4. 스키마 (P4-a 기준, 마이그레이션 `0008_drawing`)

```
drawing
  id · tenant_id · hierarchy_stable · bom_run_id(FK bom_code_run)
  drawing_no · drawing_type('plan'|'assembly') · scale · size
  current_rev(A,B,C…) · status('draft'|'review'|'approved'|'issued')
  dxf(text) · meta(jsonb) · created_at/by
  RLS: 다른 테이블과 동일한 tenant_isolation
```

## 5. 회장님 결정이 필요한 것

**Q1. P4를 a/b로 쪼갤까요?**
- 권고 **예**. P4-a가 끝나면 "치수 하나 바꾸면 도면이 바뀐다"는 장면 하나가 발표에 바로 들어갑니다. 한 번에 5항목을 열면 중간에 검증할 지점이 없습니다.

**Q2. 치수를 어디에 등록할까요?**
- (가) **기존 등록 표에 `Dim` 종류를 추가** — 새 화면 0, 회장님이 승인한 "표 모양 통일"과 같은 자리. **권고**.
- (나) 별도 Key Dimension 셋업 화면 — p38의 Design Tool 색 구분(Key/Detail/Arrangement)까지 화면으로 구현.
- (나)가 청사진에 더 가깝지만 P4 범위를 한 세션 이상 늘립니다.

**Q3. 두 번째 도면을 무엇으로 할까요?**
- (가) **조립도**(p38·p40 — 외형 + Item 표가 도면 안에). **권고** — BOM과 도면이 한 장에서 만나 "코드 하나가 도면과 BOM을 동시에 낳는다"가 눈에 보입니다.
- (나) 승인도(정면·측면 2뷰).

## 6. 정직 고지

- **단가가 샘플입니다.** 견적 문서의 합계는 Cost 카드와 일치하도록 **구조적으로** 보장되지만, 그 값 자체는 회사 실 단가가 아닙니다. 회사 표가 들어오기 전까지 견적은 "구조 시연"입니다.
- p38의 `KAD-□□□…` 슬롯과 Key Dimension의 관계(어느 슬롯이 어느 치수를 고르는지)는 **문법이 아직 정리되지 않았습니다**. P4-a는 "사이즈 행 → A~E 치수" 한 수준만 씁니다.
- DXF 파싱 검증에 `ezdxf`(Python)를 쓸 계획입니다. 샌드박스 설치가 필요하고, 회장님 PC 검증에는 불필요합니다.
- 도면 2장은 여전히 **선과 글자**입니다. 실제 제작도 수준이 아닙니다.

Q1~Q3 답을 주시면 P4-a 구현에 착수하겠습니다. 범위·순서를 바꾸실 곳이 있으면 잡아 주십시오.
